# Руководство для агентов

## Приоритет правил

При конфликте правил использовать следующий приоритет:

1. **Архитектурная спецификация проекта** (`docs/adr/`, `docs/ARCHITECTURE.md` - последний в разработке).
2. **Это правило.**
3. **Правила организации кода** (`docs/CONTRIBUTING.md`, `docs/coding-rules.md`).
4. **Существующий стиль соседнего кода.**

Не переписывать существующий код только ради соответствия этому правилу.
Правила применяются к **новому** и **изменяемому** коду.

## Стек

- Python 3.14
- Менеджер зависимостей: pip
- Линтер/форматтер: ruff
- Статический анализатор: mypy
- Брокер сообщений: Kafka
- Аналитическая БД: ClickHouse

## Команды

- Вся работа в виртуальном окружении, запуск `source .venv3-14/bin/activate`
- Установка: `pip install <package_name>`
- Тесты: `pytest`
- Линт: `ruff check .`
- Формат: `ruff format .`
- Проверка типов: `mypy .`

Другие команды в `docs/CONTRIBUTING.md`.

## Жёсткие правила

- Коммиты запрещены, только человеком

## Источники и текущее состояние

Общайтесь с пользователем на русском, если он не попросил иначе. Перед изменениями изучайте относящийся к задаче код и документацию:

- `docs/CONTRIBUTING.md` — настройка окружения, запуск контейнеров, создание топика и миграции.
- `docs/coding-rules.md` - правила организации кода.
- `docs/AI_POLICY.md` — правила использования AI. Автор вклада должен понимать результат; комментарии, issues и описания PR должны отражать собственный голос автора. Не публикуйте автоматически сгенерированный текст от его имени.
- `docs/README.md` и `docs/ARCHITECTURE.md` — назначение и архитектурные планы.
- `docs/anomaly_description.md` — требования к будущим детекторам аномалий.

Реализован приём телеметрии поездов Финляндии: Digitraffic GraphQL → Python producer → Kafka → ClickHouse Kafka Engine → materialized view → сырая таблица.

Airflow, dbt, геообогащение, baseline, детекторы аномалий, Grafana и Metabase пока описаны только в документации. Не считайте их существующими компонентами. Документация местами расходится с кодом: актуальные имена объектов и поведение проверяйте по Python, SQL и Compose.

## Правила изменений

Сначала проверьте `git status` и сохраните существующие изменения пользователя. Ограничивайте правки задачей; не исправляйте перечисленные ограничения попутно без запроса. Следуйте стилю соседнего кода: async для сетевого producer, структурированные логи через `structlog`, SQL-миграции для схемы. Не добавляйте сервисы и зависимости только потому, что они упомянуты в roadmap. При изменении поведения обновляйте связанную документацию и подходящие проверки.

## Циклы и тупики

- Одна и та же ошибка после 2 попыток фикса → остановись, покажи traceback, спроси.
- Миграция сломала тесты → остановись, не пытайся «починить» тесты под миграцию.
- Если задача требует изменения схемы БД → флаг для ручного ревью.
