## 0. Уточнение требований

### Согласованный контекст

Проект учебный: цель — развитие и демонстрация будущему работодателю навыков Data Engineering. Предполагаемые пользователи системы — диспетчеры железнодорожных станций и их системы мониторинга. Требования промышленной диспетчерской эксплуатации не установлены.

Пользователь разрешает пересмотреть или переписать существующий сбор сырых данных. Технологический стек обсуждаем: выбираем самый простой подход, расширяем его только при конкретном практическом обосновании.

### Уточнения пользователя от 2026-11-14

- Сырые данные уже собираются фоново в **локальный ClickHouse**; их можно использовать для отладки и проверки гипотез.
- Ранее изучалась выгрузка геометрии через infra-api Digitraffic, но нужные запросы не отвечали. Это сообщение пользователя; причина и текущая доступность infra-api в этой сессии не проверялись.
- Пользователь предложил исследовать архив геоданных Финляндии из OSM и локальный индекс. До этой сессии идея не была проработана; это направление исследования, не утверждённая архитектура.
- **Остановочные пункты включаются в границы перегонов.** Станции без пассажирских остановок также остаются границами согласно REQ-16.
- **Допустим результат «перегон не определён»** при неоднозначной привязке. Отдельное правило о допустимости подтверждения аномалии при неопределённой привязке пока не утверждено.
- Пользователь предоставил оба файла в `source/`, выбрал Kokkola–Ylivieska для проверки, затем разрешил сопоставить геометрию с накопленной телеметрией.

## 1. Исследование задачи

### Сценарии и требования

| ID | Согласованное требование |
|---|---|
| REQ-01 | Разрабатывать правила в порядке **№1 → №10 → №4 → №11 → №8 → №7**. Каждое завершать end-to-end до начала следующего, сохраняя возможность демонстрации системы. |
| REQ-02 | Начальный охват — все доступные пассажирские поезда: дальние и пригородные. Грузовые добавляются после шести приоритетных правил. |
| REQ-03 | Показывать ранний предварительный сигнал при первых признаках отклонения; подтверждать при выполнении условий подтверждения. Правила, допускающие немедленное подтверждение, могут сразу давать подтверждённый результат. |
| REQ-04 | Рассматривать и ошибки данных, и необычное движение. При сомнениях предпочитать показ предварительного сигнала с низкой уверенностью. Численная шкала уверенности не согласована. |
| REQ-05 | Сохранять начало, продолжение и завершение аномалии. Сохранять также предварительные сигналы, которые не подтвердились. |
| REQ-06 | Для первой демонстрации достаточно табличных данных. После реализации локального геоиндекса представление необходимо расширить. Это уточняет первоначальное пожелание о графике. |
| REQ-07 | Уведомления сейчас не отправлять; оставить их в roadmap. Механизм уведомлений пока не выбран. |
| REQ-08 | Поддержать повторный анализ сохранённой истории после изменения порогов или алгоритмов и сравнение результатов. |
| REQ-09 | Задержка обработки после получения наблюдения — до одной минуты. Время ожидания подтверждения условия аномалии задаётся отдельно. Наблюдаемые интервалы и задержки предварительно измерены; гарантий источника из этих измерений не следует. |
| REQ-10 | Первая версия работает локально. После перезапуска продолжает работу с новыми данными; пропущенные за время остановки данные не восстанавливаются. |
| REQ-11 | Для №1 использовать скорость из сырого ответа API, сравнивая её с baseline скорости. Прогноз времени прохождения и дополнительный расчёт самой скорости в первой итерации не нужны. |
| REQ-12 | В №1 учитывать положение внутри перегона простым способом и направление движения. Конкретный алгоритм не выбран. |
| REQ-13 | Индивидуальный baseline относится к одному номеру поезда на одном перегоне в разных поездках — в разные даты или время. Порог 30 наблюдений означает **30 отдельных прохождений**, а не 30 сообщений API. |
| REQ-14 | При недостатке индивидуальной истории переходить к групповому baseline согласно исходному описанию. Если достаточного baseline нет, показывать «недостаточно данных». |
| REQ-15 | Подтверждённое замедление завершается после устойчивого возвращения скорости к норме, а не после одной нормальной точки. Длительность не определена. |
| REQ-16 | Перегон — участок между любыми соседними железнодорожными станциями и остановочными пунктами, независимо от остановок конкретного поезда. |
| REQ-17 | При неоднозначной геопривязке допустим результат «перегон не определён». |

### Текущее состояние и границы исследования

Проверены `producer/main.py`, обе SQL-миграции, `docker-compose.yml`, фактическая схема локальной БД и наличие работающих контейнеров. Реализован путь Digitraffic GraphQL → Python producer → Kafka → ClickHouse Kafka Engine → materialized view → сырая таблица.

- Producer запрашивает `currentlyRunningTrains` с `trainNumber`, `departureDate`, `version` и **одной последней точкой** `trainLocations` (скорость, время, координаты). Интервал по умолчанию — 15 секунд; фактическое значение переменной окружения не проверялось.
- Kafka topic: `train-locations`, ключ сообщения содержит номер поезда, без даты отправления.
- БД: `rolling_anomalies_db`; объекты: `kafka_train_locations`, `kafka_to_raw_train_locations_mv`, `raw_train_locations`.
- Сырая таблица: `train_number`, `timestamp`, `departure_date`, `lat`, `lon`, `speed`, `version`, `received_at`. `ReplacingMergeTree`, ключ `(train_number, timestamp)`, дневные партиции, TTL 730 дней. Дата отправления не входит в ключ. Это существующие настройки, не новые решения о хранении.
- `received_at` заполняется на стороне ClickHouse, а не в момент получения HTTP-ответа producer. Разность с `timestamp` нельзя считать чистым временем обработки после получения наблюдения.
- Категории, маршруты и станции producer не запрашивает. «Сырые» строки уже преобразованы SQL: исходный JSON целиком в этой таблице не сохраняется. Проверка отсутствующих/ошибочных полей источника ограничена этими преобразованиями.
- Часовой пояс ClickHouse — UTC. Запросы к БД выполнялись только на чтение, с ограничениями 30 секунд и два потока. Работающий сбор не останавливался.

Airflow, dbt, геообогащение, baseline, детекторы и средства визуализации не считаются реализованными. Их упоминание в документации не обязывает включать их в новую архитектуру.

### Профиль накопленной телеметрии, 2026-11-14

Измерения — снимки результатов запросов при работающем сборе, а не неизменяемый экспорт всей БД. Первые агрегаты получены около 09:24 UTC; для последующих использовалось `timestamp < '2026-11-14 09:24:00'`. Из-за поступления/слияния строк количества между запросами немного различаются.

| Различные `(train_number, timestamp)` в первом запросе | 334 025 |
| Номера поездов | 1 446 |
| Сочетания `(train_number, departure_date)` | 2 086 |
| Время наблюдений, UTC | 2026-11-10 06:28:43 — 2026-11-14 09:23:49 |

| NULL-координаты / пары `(0,0)` | 0 / 0 |
| Скорость: медиана / p90 / p99 | 71 / 138 / 162 км/ч |
| Максимальная скорость | 294 км/ч |
| Строки с нулевой скоростью | 43 520 |

Для интервалов строки читались с `FINAL`, группировались по номеру и дате отправления и сортировались по `timestamp`; первый нулевой интервал исключался. Получено 331 941 положительных интервалов: медиана 17 с, p90 28 с, p95 34 с, p99 55 с; 2 926 интервалов больше минуты, 527 больше пяти минут, максимум 43 349 с. Пропуски нельзя без проверки приписывать только источнику: возможны остановки локального сбора и возвращение поезда в наблюдаемую выборку.

Для 334 027 строк с `FINAL` разность `received_at - timestamp`: медиана 13 с, p90 26 с, p99 18 663 с; 29 453 строки (около 8,8%) больше минуты; отрицательных разностей не найдено. Причины больших разностей не исследованы; возможны устаревшие точки источника, доставка/накопление и особенности заполнения `received_at`. Это не проверка выполнения REQ-09.

Два примера скоростей для последующего анализа: поезд 60954, 2026-11-12 11:56:14 UTC — 294 км/ч, `(lat=60.200017, lon=24.942134)`; поезд 102, 2026-11-14 05:41:50 UTC — 251 км/ч, `(60.194491, 24.922383)`. Они не признаны ошибками или подтверждёнными аномалиями.

Вывод: история пригодна для исследования плотности телеметрии и геопривязки. Достаточность baseline не доказана: строки и даты не равны прохождениям; индивидуальный порог 30 прохождений ещё не проверялся. Статистики включают неизвестные категории поездов, поскольку категории не сохраняются текущим сбором.

### Сопоставление справочника с OSM

В PBF найдено 19 607 ways с `railway=rail`. Это количество объектов OSM, не перегонов или физических путей. Среди них 5 824 с `service=yard`, 1 966 `siding`, 2 891 `spur`, 367 `crossover`; у 8 559 `service` отсутствует. Тег `usage=main` есть у 6 310, `branch` у 1 955, у 10 747 `usage` отсутствует. Пустой тег сам по себе не доказывает отсутствие эксплуатационного значения.

Первоначальный поиск только по `railway=station/halt` дал совпадение кода для 209 из 509 объектов (206 с единственным кандидатом). Примеры `uic_ref` имеют другой формат, чем числовой `stationUICCode`; прямое сравнение не дало совпадений. Правило преобразования UIC-кодов не утверждено.

Расширенный поиск выполнялся по всем объектам с `railway:ref`: сравнивались `stationShortCode` и `railway:ref` в верхнем регистре. Для расстояний использовались только OSM nodes с координатами; при нескольких кандидатах для исследовательской статистики выбирался ближайший по расстоянию на сфере.

- Совпадения найдены для **504 из 509** (около 99%); у 38 кодов несколько OSM nodes.
- Медианное расстояние между координатами Digitraffic и ближайшего совпадения — 5 м, p90 — 64 м, максимум 721 м.
- Ближайшие совпадения относятся к `station` (167), `halt` (33), `site` (122), `yard` (120), `crossover` (40), `junction` (13), `stop` (3); у шести нет тега `railway`.
- Пассажирские: найдено 206, не найдено 3.

### Проверка коридора Kokkola–Ylivieska

Пользователь выбрал этот участок для исследования. Координаты Digitraffic: Kokkola (`KOK`) — `(63.834429, 23.131096)`, Ylivieska (`YV`) — `(64.071898, 24.540593)`.

Методика предварительного топологического эксперимента:

1. Из PBF извлечены ways с `railway=rail` и их узлы; найдены все 107 367 запрошенных координат узлов.
2. Рёбра соединяли соседние OSM node IDs. Простое пересечение линий на карте не создавало дополнительного соединения.
3. Построен ненаправленный граф; длины и проекции приблизительно вычислялись в метрах по формуле `x = lon * cos(64°) * 111195`, `y = lat * 111195`. Это исследовательская аппроксимация, не выбранная рабочая CRS.
4. Конечные станции привязывались к ближайшим доступным узлам графа. Поиск кратчайшего пути — Дейкстра. Реальное направление эксплуатации и маршрут конкретного поезда не проверялись.
5. Для поиска промежуточных станций проверены объекты справочника рядом с найденным путём, затем расстояния уточнены проекцией на линии. Первоначальные расстояния до ближайшего узла (например, 335 м для Riippa) **не являются** расстояниями до пути: после проекции Riippa находится примерно в 0,1 м от линии.

### Сопоставление сохранённой телеметрии с коридором

Выполнено после разрешения пользователя «Вперед». Из ClickHouse экспортирована прямоугольная выборка:

```sql
SELECT train_number, departure_date, timestamp, lat, lon, speed
FROM rolling_anomalies_db.raw_train_locations FINAL
WHERE lat BETWEEN 63.75 AND 64.15
  AND lon BETWEEN 23.05 AND 24.65
FORMAT JSONEachRow;
```

В этом запросе **не было временной отсечки**: результат отражает состояние базы на момент исследования 2026-11-14; даты отправления в выборке — 11–14 ноября. Для точного повторения нужен сохранённый экспорт; повторный запрос к растущей БД даст другие числа. Фильтр прямоугольника включает посторонние участки: точки вне выбранного коридора нельзя автоматически считать ошибочными.

Для проекции взят путь ≈78,302 км по графу `usage=main OR service=crossover`. Для каждого наблюдения найдена ближайшая точка на этой линии и расстояние вдоль неё. Это проверка геометрии, **не реализация последовательного map matching**: предыдущие точки не использовались для выбора кандидата.

|---|---:|
| Точки в прямоугольной выборке | 4 359 |

Статистики расстояний условны на фильтре ≤100 м и не характеризуют всю телеметрию. Категории поездов не установлены, поэтому результаты нельзя выдавать за проверку только пассажирских поездов.

**Неоднозначность кандидатов.** Для локальных рельсовых отрезков из OSM искались проекции не дальше 30 м. В исследовательский подсчёт брались внутренние проекции (параметр отрезка между 0,05 и 0,95), чтобы уменьшить влияние соседних сегментов одной линии. Точка считалась неоднозначной, если кроме ближайшего кандидата есть другой с разницей расстояний не более 10 м и расстоянием между самими проекциями не менее 2 м.

По этой эвристике 2 000 из 3 311 точек (около 60%) имеют несколько близких кандидатов. Среди 2 555 точек со скоростью >20 км/ч и дальше 500 м вдоль линии от приближённых станционных отметок — 1 331 (около 52%). Это **доля геометрической неоднозначности по выбранной эвристике**, не доля ошибочной привязки и не доказательство, что все кандидаты — параллельные физические пути. 30/10/2/100/500 м и 20 км/ч — исследовательские параметры, не утверждённые пороги.

Общее направление задавалось ретроспективно знаком разности последнего и первого положения: 11 в сторону Ylivieska, 9 обратно. Среди 2 836 соседних пар с интервалом ≤60 с не найдено шагов назад больше 50 м относительно этого направления. Это не независимая проверка детектора №10, не проверка онлайн-определения направления и не доказательство отсутствия GPS-ошибок.

## 2. Предметная модель

- **Аномалия:** выявленное отклонение, сигнализирующее о возможной внештатной ситуации. Сигнал не доказывает причину; групповое замедление само по себе не доказывает неисправность пути.
- **Перегон:** участок между соседними станциями или остановочными пунктами; не участок между остановками рейса. Kokkola–Ylivieska в исследовании — коридор из восьми перегонов, а не один перегон.
- **Прохождение:** отдельное прохождение поездом перегона; единица счёта исторических наблюдений для порога 30. Правила определения границ прохождения ещё не заданы.
- **Индивидуальная история:** один номер поезда, перегон и направление в разных поездках. Отдельная поездка и повторяющийся номер — разные понятия; технические ключи открыты.
- **Baseline:** профиль нормальной скорости с учётом положения и направления. Детали групповых срезов, статистик и fallback требуют спецификации; предложения исходного документа остаются исходными вариантами.
- **Предварительный / подтверждённый:** степень подтверждения сигнала. Начало, продолжение и завершение описывают его течение во времени. Это разные характеристики; схема состояний ещё не принята.
- **Недостаточно данных:** результат, сообщающий об отсутствии достаточного основания для статистического сравнения; его представление в модели ещё не выбрано.

Существенные случаи для дальнейшего анализа: нормальное ускорение и торможение, ошибочные координаты и скорость, пропуски наблюдений, повторные прохождения, перезапуск во время активной аномалии. Нельзя считать отсутствие наблюдений доказательством непрерывного замедления — это выявленный риск, правила обработки пока открыты.

## 3. Проектирование архитектуры

### Текущий статус

Новая архитектура не выбрана. Согласованы требования и последовательность демонстрационных итераций. Существующий сбор и исходные данные предварительно проверены. Следующий шаг — обсудить зоны станций и переходы между перегонами (Q-10), затем согласовать модель геопривязки; сравнение обработки и хранения системы в целом ещё впереди.

Два уровня подтверждения не означают обязательные два сервиса или два физических контура. Это пока требование к поведению результата.

### Зависимости и риски

- Уже №1 требует определения перегона, направления и положения внутри него. Географическая привязка нужна до завершения первой итерации, хотя отображение может оставаться табличным. Нужен ли сразу полноценный локальный геоиндекс, не решено.
- Начальная история может быть недостаточной. Согласованное поведение — «недостаточно данных»; это не доказывает работоспособность обнаружения, поэтому критерий демонстрации детектора ещё нужно определить.
- Сравнение с единой скоростью всего перегона может смешать нормальное торможение и аномалию. Пользователь потребовал учитывать положение, но без сложных алгоритмов.
- Ошибки телеметрии могут имитировать аномалии движения. Приоритет раннего сигнала не означает автоматическое подтверждение на недостоверных данных.
- Локальный запуск и допустимые пропуски ограничивают полноту истории. Допуск пропусков не определяет автоматически политику сохранённого состояния.
- Доступность подходящих ограничений скорости и связь с типом подвижного состава ещё не проверены; простота правила №11 не доказана.

### Альтернативы

Сравнены два источниковых подхода:

| Подход | Преимущество | Ограничение |
|---|---|---|
| Только OSM | Геометрия, топология и объекты станций в одном источнике | Типы OSM не совпадают напрямую с понятием станции в Digitraffic; нужна связь с расписаниями и объединение объектов одной станции. |
| OSM + справочник Digitraffic | Коды и типы Digitraffic задают предметные объекты, OSM даёт геометрию и связность | Нужны сопоставление, разрешение нескольких кандидатов, обработка несовпадений и версии обоих источников. |

**Рекомендация агента, не утверждена:** гибрид OSM + Digitraffic. Состав границ перегонов определять по справочнику, искать географические соответствия в OSM без ограничения только тегами `station`/`halt`.

Предложенный поток: версия выгрузки → железнодорожная сеть → сопоставление станций → участки между соседними станциями → локальный пространственный индекс. Для точки: несколько близких кандидатов → проверка согласованности с предыдущими точками → перегон, направление, положение либо неопределённость. Предлагался локальный `STRtree` как вариант индекса для перестраиваемого снимка; библиотека и формат хранения не выбраны.

**Последняя рекомендация после эксперимента:** для №1 проверить «перегон + направление + положение вдоль общей геометрии», без обязательного определения конкретного физического пути. Если все кандидаты относятся к одному перегону, неоднозначность пути не обязательно означает неоднозначность перегона. Если к разным — возвращать «не определён». Пользователь ещё не утверждал эту модель.

Ограничения предложения:

- Индекс находит географически близкие объекты, но сам не определяет топологическую принадлежность и маршрут.
- Между одной парой станций могут быть разные маршруты; идентификатора только из двух кодов может не хватить.
- Нельзя принудительно подгонять наблюдаемое движение под ожидаемое направление: это может скрыть аномалию №10.
- Пока не решены зоны станций, привязка около развязок, построение общей геометрии параллельных путей, переносимость на другие коридоры и обновление версий геоданных.
- Наличие `maxspeed` в OSM не подтверждает пригодность источника для №11: нужны актуальность, применимость к составу и отдельное исследование.

Способ обработки с состоянием, расчёт baseline и инструменты отображения не выбраны. Добавление технологий должно иметь практическое обоснование.
