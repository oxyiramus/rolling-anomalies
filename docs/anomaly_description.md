# Описание аномалий

Аномалия в контексте проекта Rolling Anomalies - это выявленное отклонение в данных, которое сигнализирует о неполадках и внештатных ситуациях в процессе движения поездов. Данный документ описывает эту сущность и фиксирует правила, по которым различные аномалии выявляются.

## Срезы

Для части аномалий необходимо понятие "срез" поезда. Срез - это группа поездов, которые совпадают с рассматриваемым поездом по одной/нескольким характеристикам. Основные характеристики, по которым фиксируются срезы, приведены ниже.

1. По категориям поездов:
   1. Пассажирский дальний
   2. Пассажирский пригородный
   3. Грузовой срочный
   4. Грузовой обычный
2. По перегонам/маршрутам

Эти срезы необходимо заложить изначально. Другие возможные срезы описаны в пункте **Как устроить baseline и срезы**

## Список аномалий

1. Время прохождения (или средняя скорость, посмотреть что будет удобнее считать) > baseline для этого же поезда в это же время суток в течение N минут на X км/ч. Если по конкретному поезду на конкретном перегоне накоплено меньше 30 записей, то считать не относительно самого поезда, а относительно группы поездов такого же среза. Срезы описаны в предыдущем пункте.

2. Скорость == 0 в течение N минут, на станции, где по расписанию нет остановки (включая станции вне маршрута)

3. Скорость == 0 дольше чем нужно на станции из расписания в течение N минут

4. Скорость \~ 0 (определить порог, например 5 км/ч) в течение N минут, поезд на перегоне а не на станции

5. Резкое падение скорости (понять как снижается скорость перед станцией, и что считать "резко", отдельно по срезам)

6. Накопление отставания от расписания на Y минут по станциям

7. Несколько поездов на перегоне одновременно со скоростью 0 или аномально низкой (определить что есть "низкий" порог) = проблема пути

8. Данные о местоположении поезда перестали поступать на N минут - data quality

9. Координаты не соответствуют ожидаемому маршруту (для пассажирских)

10. Поезд двигается в противоположную сторону от маршрута по перегону в течение N минут (сравнение вектора движения с вектором станция -> следующая станция)

11. Скорость на перегоне превышает максимально допустимую для типа подвижного состава (взять из infra-api)

12. Поезд отправился со станции раньше расписания на N минут (для пассажирских)

## **Классы аномалий**

| **Класс**        | **Аномалии**    | **Принцип обнаружения**                                     |
| ---------------- | --------------- | ----------------------------------------------------------- |
| Статистические   | 1, 5, 6         | Сравнение с baseline и динамикой                            |
| Состояние поезда | 2, 3, 4, 10, 12 | Состояние и последовательность событий                      |
| Инфраструктурные | 7, 11           | Сопоставление поездов, ограничений и инфраструктуры         |
| Качество данных  | 8, 9            | Контроль полноты, актуальности и согласованности телеметрии |

## **Как реализовать каждый класс аномалий**

### **Статистические аномалии: №1, 5, 6**

Наиболее оптимально заранее подготовить таблицы baseline, а в realtime только получать нужный профиль и сравнивать текущие показатели с ним.

**№1. Отклонение от baseline**

Имеется в виду время прохождения *больше* baseline либо скорость *ниже* baseline.

Для индивидуального считаем так:

- если есть не менее 30 исторических прохождений конкретного поезда по конкретному перегону — используем индивидуальный baseline;
- иначе переходим к групповому baseline;
- сравниваем время прохождения или скорость с порогом отклонения.

Для группового - так. Срез здесь может включать:

- категорию поезда;
- перегон или маршрут;
- будни/выходные;
- пик/не пик;
- сезон;
- оператора;
- чётное/нечётное направление.

Но я бы не создавала все возможные комбинации автоматически. При большом количестве измерений многие комбинации окажутся слишком редкими.

Нужна иерархия fallback:

1. Индивидуальный поезд + перегон.
2. Категория поезда + перегон + подходящие временные срезы.
3. Категория поезда + перегон.
4. Общий baseline перегона.

Для каждого baseline хранить:

- количество наблюдений;
- период расчёта;
- медиану;
- MAD;
- версию;
- уровень детализации.

Это позволит не только обнаруживать отклонение, но и оценивать уверенность детекции.

**№5. Резкое падение скорости**

Здесь нужен не один порог для всех поездов, а модель нормального замедления перед станцией. Можно использовать расстояние до следующей станции, скорость и тип поезда. Для каждого среза строить профиль нормального торможения. Realtime-процессор сравнивает фактическую динамику скорости с ожидаемой.

**№6. Накопление отставания**

Это уже не разовая проверка, а отслеживание временного ряда:

- вычислить опоздание на текущей станции;
- сравнить с опозданием на предыдущей;
- определить, растёт ли оно;
- проверить достижение порога Y минут.

Для этого удобно хранить состояние поезда и обновлять его при каждом событии прибытия или прохождения контрольной точки.

### **Аномалии состояния поезда: №2, 3, 4, 10, 12**

Эти правила хорошо подходят для онлайн-обработки с состоянием и таймерами. Важный момент: не нужно ждать N минут, а потом начинать расчёт. Таймер запускается сразу, когда условие впервые становится истинным. Новые события подтверждают или сбрасывают его.

Аналогично:

- №2 — остановка вне разрешённой станции;
- №3 — превышение допустимого времени стоянки;
- №10 — противоположное направление движения;
- №12 — отправление раньше расписания.

Для №10 я бы сравнивала не просто географический вектор между двумя координатами, а направление движения вдоль геометрии перегона. На извилистом участке направление по прямой может дать ложный результат.

Для №12 важно иметь достоверное событие отправления, а не делать вывод только по первой координате после стоянки.

### **Инфраструктурные аномалии: №7, 11**

**№7. Несколько поездов на перегоне движутся аномально медленно.**

Это задача для Segment processor.

Он должен хранить актуальное состояние поездов по каждому перегону и проверять:

- сколько поездов находится на перегоне;
- сколько из них стоят или движутся медленнее порога;
- как долго сохраняется такая ситуация;
- не объясняется ли она расписанием или обычной эксплуатационной ситуацией.

Важно: совпадение нескольких остановок — сигнал возможной проблемы инфраструктуры, но ещё не доказательство. Лучше сначала формировать `suspected_infrastructure_issue`.

**№11. Превышение максимально допустимой скорости.**

Это, пожалуй, самый простой случай для быстрого детектора:

- получать ограничения скорости из infra-api;
- хранить актуальные ограничения локально;
- сопоставлять поезд, перегон и тип подвижного состава;
- сравнивать текущую скорость с допустимой.

Обновление справочника ограничений должно иметь версию и время действия. Нельзя продолжать использовать устаревшее ограничение без контроля его актуальности.

### **D. Качество данных: №8, 9**

**№8. Отсутствие координат**

Тут нужен отдельный механизм таймеров, потому что при отсутствии событий consumer не получает ничего, что могло бы запустить проверку.

Нужно:

- знать, когда ожидать следующее событие;
- хранить время последней телеметрии;
- запускать периодическую проверку истёкших таймеров.

**№9. Координаты не соответствуют маршруту**

Проверять можно сразу при каждом событии:

- расстояние до ожидаемой геометрии маршрута;
- принадлежность допустимому коридору;
- согласованность с предыдущей позицией;
- наличие альтернативного допустимого маршрута.

Один ошибочный GPS-пакет не должен сразу приводить к серьёзной аномалии. Нужны порог и, возможно, подтверждение несколькими последовательными точками.

## **Как устроить baseline и срезы**

Можно разделить измерения на три группы.

| **Измерение**    | **Как использовать**                                       |
| ---------------- | ---------------------------------------------------------- |
| Категория поезда | Основное измерение baseline                                |
| Перегон          | Основное измерение baseline                                |
| Направление      | Основное измерение baseline                                |
| Будни/выходные   | Контекстный срез                                           |
| Пик/не пик       | Контекстный срез                                           |
| Сезон            | Контекстный срез, если есть статистически значимая разница |
| Оператор         | Контекстный срез, если есть статистически значимая разница |
| Конкретный поезд | Индивидуальный baseline при достаточном объёме данных      |

### **Пик и сезонность**

Нельзя зашивать пик и сезон в коде как неизменные календарные условия.

**Пик:**

- собрать историческое количество поездов и их фактические интервалы движения;
- построить распределение по времени суток и дням недели;
- определить периоды устойчиво высокой интенсивности;
- зафиксировать полученные интервалы в таблице профилей.

В итоге 7–9 и 16–18 могут оказаться правильной начальной гипотезой, но данные должны её подтвердить.

**Сезон:**

- исследовать распределения скорости и времени прохождения перегонов по месяцам;
- проверить, есть ли устойчивые сезонные различия;
- определить интервалы, которые действительно влияют на нормальное движение;
- версионировать сезонный профиль.

Не стоит автоматически считать, что календарная зима — единственный значимый фактор. Для железной дороги фактические условия могут зависеть от погоды, состояния инфраструктуры и региона.

### **Как хранить baseline**

Отдельная таблица, условно `segment_baselines`:

| **Поле**             | **Назначение**        |
| -------------------- | --------------------- |
| `segment_id`         | Перегон               |
| `train_category`     | Категория поезда      |
| `direction`          | Направление           |
| `day_type`           | Будни/выходные        |
| `peak_profile`       | Профиль нагрузки      |
| `season_profile`     | Сезон                 |
| `operator_id`        | Оператор              |
| `sample_count`       | Количество наблюдений |
| `median_travel_time` | Медианное время       |
| `median_speed`       | Медианная скорость    |
| `mad_speed`          | MAD скорости          |
| `baseline_version`   | Версия профиля        |
| `calculated_at`      | Время расчёта         |

Необязательно заполнять каждую комбинацию измерений. Для редких комбинаций должна срабатывать описанная выше иерархия fallback.

**Отдельно:** правило №1 требует уточнения. Если мы хотим обнаруживать замедление ещё до завершения прохождения перегона, нельзя ждать фактического `travel_time`. Нужно оценивать прогнозное время прохождения по текущей скорости и оставшемуся расстоянию. После завершения перегона можно уже проверить фактическое время и обновить историю.

Это хороший пример, почему realtime detection и batch analytics должны быть разными слоями.

## **Первая версия**

Не реализовывать все 12 правил одновременно. Для портфолио особенно важно показать, что система умеет обрабатывать разные типы событий. Первая итерация может быть такой:

| **Правило**                             | **Почему в первой версии**                                     |
| --------------------------------------- | -------------------------------------------------------------- |
| №4 — почти нулевая скорость на перегоне | Наглядная stateful-детекция с таймером                         |
| №10 — движение в обратном направлении   | Показывает работу с геометрией и последовательностью координат |
| №11 — превышение допустимой скорости    | Быстрое правило с внешним справочником                         |
| №8 — отсутствие телеметрии              | Показывает обработку отсутствующих событий и таймеры           |
| №1 — отклонение от baseline             | Демонстрирует статистическую детекцию                          |
| №7 — групповое замедление на перегоне   | Демонстрирует межпоездную агрегацию                            |

Остальные правила можно будет добавить на уже готовые механизмы.
